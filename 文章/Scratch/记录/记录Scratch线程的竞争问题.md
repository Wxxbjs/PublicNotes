# 前引入
众所~~但不~~周知，线程在计算机科学中存在一种叫“数据竞争”的问题
此问题类似：
多个线程共享同一个数据进行读取引发的竞争问题。
此问题的根本就是线程让步会中断操作，但有些代码，或者说操作并非是“原子性”的
即使是最简单的“++i”指令
因此就会导致一下现象：
假设现在需要4个线程a,b,c,d在依次递增一个共享变量x，每个线程就单纯执行“++x”的操作，x初始为0（执行顺序不关心）
当执行到a线程时，CPU将x的值读取出来，递增，但此时线程被要求让步，CPU将当前寄存器的状态保存下来，执行b线程，此时x的值是0；而b线程直接完成了++i的操作，并写回x，再让步，执行c线程，此时x是1；类似的，c和d线程都完成了++i的操作，并正确赋值，此时x应该是3
但回到a线程时，CPU读取保存下来的寄存器状态，此时写回去的应该是第一次执行a线程时x+1的结果，那么写回去的x就直接变成了1而不是正确的4
因此x的值就是错的，这就是所谓“数据竞争”

# 正文
但说了这么多，和Scratch有什么关系呢。
在了解到了“数据竞争”的问题，我就开始担心Scratch的线程会不会有类似现象

但我进行了很长时间的针对性测试，都没有哪怕出过一次问题。
而且实际上你和我到现在都没有哪怕见过一个人公开发表过共享数据出错的问题
难道我学的东西是假的？解释模型错了？或许Scratch以某种方式解决了“数据竞争”的问题？

我能想到的就是Scratch对线程的让步动了什么手脚，从而不会出现类似连++i都会丢状态的问题

我猜测“Scratch的让步是单个积木级别的”
也就是说，无论一个积木的操作有多耗时，Scratch只会在这个积木执行前或执行完才考虑当前线程让步不让步，而不是在单个积木的执行过程中就中断（除中途跳转到新的积木，这会导致Scratch考虑让步）
所以赋值等局限在单个积木上的操作是“原子性”的，至少不会出现赋值赋到一半就中断的问题
因此，只要进行了赋值操作，变量的值就一定可以保证是计算表达式计算出来的结果，而不是一种不安全的过程值
所有需要原子操作的计算任务，如果不容忍计算时的过程值泄漏，但容忍旧值复用
那么这种写法：
```
[将[计算结果]设为()]
//省略一堆非常复杂的操作
[将[共享变量]设为(计算结果)]
```
即可解决原子性的问题
这样一来，几乎不用担心所谓的“数据竞争”的问题

# 结语
虽然这种“数据竞争”的问题在Scratch几乎不用担心
但是由于Scratch原生并没有局部变量这种随作用域的东西，因此大多数需要使用临时变量的场景，比如经典的i,j,k等遍历指针，都是新建新建再新建一堆i,j,k变量来实现
我相信你们肯定都知道：整个线程上下文，即一路上调用的若干自制积木，不得使用同一个i变量进行遍历
即类似：
```Scratch
[定义 函数1]{
    [将[i]设为(1)]
    [重复执行(10)次]{
        //积木段
        [将[i]增加(1)]
    }
}
[定义 函数2()]{
    [将[i]设为(1)]
    [重复执行(10)次]{
        [函数1];
        [将[i]增加(1)]
    }
}
```
这种明显是错误的写法

但是还有一种更隐式的错误：
由于存在线程，即使你给自制积木设置warp模式来尽可能一次性执行完，但是还是存在让步的可能
因此一个自制积木内部的变量状态会被“暴露到外部允许访问和修改”（其实是让步后的一种操作的现象，即对自制积木内部使用的变量的数据进行篡改的行为）
因此但凡外部不小心修改了自制积木依赖的变量的数据，那么自制积木的行为就可能非常不可控
所以，不但不能在单个线程上下文复用一个临时变量，你也不应该在多个线程之间复用一个临时变量
除非你的自制积木内部的数据量较小，或者你可以控制这种问题带来的问题
~该错误的提醒是我发现身边的Scratcher对此问题的原理不了解而启发的~

但还没完
“不应该在多个线程之间复用一个临时变量”就约等于说“不应该多次调用自制积木”
（原因很简单：你几乎不可能不在自制积木内使用变量）
（此时不用跨线程使用变量可以理解为不能跨线程调用自制积木）
那么此时自制积木作为函数可以被同时多次调用的意义在那里。
再加上Scratch没有局部变量的缺陷
就引出了一个非常棘手的问题：
肯定存在一种需求需要类似：
```cpp
void dfs(/*某些参数*/){
    //某些状态转移
    for(int i=0;i<n;++i){
        if(/*某种布尔表达式*/){
            dfs(/*某些参数*/);
        }
    }
    //某些状态转移
}
```
这种不定深度的递归式的写法，
此时就需要一个完全独立于其他函数的变量i（因为递归的层数不可控，你又不可能提前新建若干变量）
但你知道的，Scratch完全几乎没法动态创建一个“变量积木”
就算用列表模拟栈帧来模拟（梦回汇编时代。不是。）
那么我问你：怎么解决多线程递归且需要一个至少独立在单个自制积木内的变量？
难不成多栈帧？
问题似乎越来越麻烦了。
BUT，
对于这种需求，我给出一个“持续由线程上下文构造调用栈唯一ID并进入函数”的技术
很简单：
我们强行约定所有函数必然有一个参数叫“ID”
这个ID的性质：任何时刻，所有的正在执行的自制积木的ID绝对不可能出现两个同样的（下文有维护方法）
那么此时单个自制积木用这个ID去内联变量名进行编码，再套一个KV数据结构（可全局）即可
那么问题就变成了构造一个ID系统
ID系统最朴素的实现方法是：删除ID时加入到回收ID列表+如果有空闲ID就复用+没有就新建全新
（只不过这个方法不太优雅，需要多带一个ID参数，还要搞生成ID的调用函数，在Scratch这种不能传入“积木段”的环境下写出来的代码就很耦合）

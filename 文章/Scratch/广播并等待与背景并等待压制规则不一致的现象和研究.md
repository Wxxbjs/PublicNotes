现象就是：
解释模式下：
[ 广播 ( 消息1 ) 并等待 ] **一般会被**开启warp模式的自制积木压制
[ 换成 ( 背景1 ) 背景并等待 ] **一般会被**开启warp模式的自制积木压制

[ 广播 ( 消息1 ) 并等待 ] **不会被**开启warp模式的自制积木压制
[ 换成 ( 背景1 ) 背景并等待 ] **会被**开启warp模式的自制积木压制

表格：

|积木 \\ 模式|解释模式|编译模式|
|:-:|:-:|:-:|
|广播并等待|**一般会被**warp模式压制|**不会被**warp模式压制|
|切换背景并等待|**一般会被**warp模式压制|**会被**warp模式压制|

以及出自runtime.js的关于 Runtime 这个class的实现的部分接口
```js
/**
 * Return whether a thread is currently active/running.
 * @param {?Thread} thread Thread object to check.
 * @return {boolean} True if the thread is active/running.
 */
//活跃线程判定
//有堆栈，且当前不是失活状态
//且还在线程池中
isActiveThread (thread) {
    return (
        (
            thread.stack.length > 0 &&
            thread.status !== Thread.STATUS_DONE) &&
        this.threads.indexOf(thread) > -1);
}

/**
 * Return whether a thread is waiting for more information or done.
 * @param {?Thread} thread Thread object to check.
 * @return {boolean} True if the thread is waiting
 */
//不是活跃线程
//或者是异步搁置线程
//或者被帧搁置
isWaitingThread (thread) {
    return (
        thread.status === Thread.STATUS_PROMISE_WAIT ||
        thread.status === Thread.STATUS_YIELD_TICK ||
        !this.isActiveThread(thread)
    );
}
```
简单的说：广播和背景的源码除了事件不同以外，等待部分的逻辑是完全相同的
基于事实，我简单的将其合并为一个来说：
尽管源码中等待中明显有写yieldTick和yield两种搁置方法，但是由于各种原因，触发yieldTick的条件极为苛刻（接管的线程组必须同时陷入异步搁置或帧搁置或**不活跃线程**（相关条件也很刁钻，见上runtime.isWaitingThread方法的实现））
所以帧搁置的强制让步其实并不常见。
所以连我都以为广播和背景都只有一种让步策略了。
所以说，**在一般情况下**，广播和背景几乎不可能不被warp模式压制。
但是呢。
调度文章肯定很多地方都得改相关说辞。
虽然暂时我没有时间和精力深究到底这个判定意味这什么，但至少我先记录了。

而且比较有意思的是：
如果你在warp模式下的自制积木下进行广播并等待，而接受积木下调用翻译积木（不是走真·等待一帧的逻辑，而是真的请求一个耗时的翻译任务，当然你也可以自己模拟一个耗时的异步任务，但是不重要。关键在**长期陷入异步**上。）
而你尝试观察线程的话，可以发现初次并等待的时候会卡一下，而后续的渲染帧就不卡了
而且这并不是因为翻译积木返回了导致接收线程爆炸了回调了原等待线程不执行了（？），
而是出现了["STATUS_YIELD_TICK ","STATUS_PROMISE_WAIT "]的线程状态（前者是等待广播的线程，后者则是接收广播并导致一个翻译异步任务的线程）
这似乎也解释的通：
按照上面的逻辑，因为第一次等待时只是发出去了这些线程，并没有执行任何接收广播的线程，所以此时接收线程的状态一定是RUNTIME，所以此时肯定会调用yield方法来单纯搁置，然后就warp压制了。
但是挺过了这个帧以后，接收线程一定会执行，接收线程就一定会长期陷入STATUS_PROMISE_WAIT状态
而后等待线程再来检查，发现满足全是异步线程的条件，故开始调用yieldTick来搁置
所以以后就不会卡死了。
嗯对太神秘了知道吗。
也算是一个小证据吧。

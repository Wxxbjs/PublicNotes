# 小前言
其实我在想一个问题。
凭什么只能有 LRF （一渲染帧内只有一个逻辑帧）和 LRMF （一个渲染帧内有死多个逻辑帧）
明明可以 LRSF 的。（ LRS 是 LR 的复数形式，即一渲染帧内有多个逻辑帧，且数量是可控的）
为什么可以呢。
只要保证不开加速模式、单个线程（或单个逻辑帧内）不超时超狠了，那么实际上逻辑帧的次数完全受到渲染标记的控制
而渲染标记无非对应渲染操作，基本是运动积木、外观积木之类的积木。
所以为何不可以精确控制渲染操作呢。
这样一来就可以允许很多事情，
比如因为渲染帧内部有了多个逻辑帧，所以用广播伪造的自制积木可能还真可以实现调度严格。（如果严格控制的话）
所以某些“立刻多角色执行”的需求可能还真可以以又一种方式绕过、实现
（**注意**：由于还是涉及底层选择问题，无法轻易的迁移，这部分的证明基本可以说是“Scratch的调度内核的追加序+广播自己的打断特性”导致的，仅表明上提供了又一种可能的绕过手段，而不是模拟调度这种需到不能再虚的目标。）

另外，为了整理，也方便描述和理解，我将解释一下所谓的 LRF 系列的术语
# LRF
LRF 系列的术语是一个用于简述调度环境的术语。  
完整展开是 Logic Rendering Frame （字面意思，逻辑帧与渲染帧，直接硬翻译就叫“逻辑渲染帧（的行为环境）”）  
其中如果直接使用 Logic Rendering Frame（LRF），则是最常规的调度模型，即一个渲染帧内只有一个逻辑帧，且不开启加速模式、必然有刷（必然有标记渲染标记）。  （朴素可玩可看的项目几乎都是 LRF ，也有默认的意味。）
而 LRMF 的完整展开是 Logical Rendering Mixed Frame ，即加速模式、无刷（完全没有标记渲染标记）但非加速模式时的环境（也称为纯算法环境（因为纯实现算法时只涉及变量、列表、运算，不涉及渲染操作，自然也有这种说法），所以 LRMF 更多在纯算法作品里被运用（其实有点本末倒置，因为其通常没有渲染操作，自然就是 LRMF ））  
而 LRSF 无非就是刚刚说的了——完整展开叫 (Logical Rendering)s  Frame  
其实严格上应该叫 LSRF （Logicals Rendering Frame）。但是我觉得 LRSF 更好看（~~好吧其实就是为了和 LRMF 保持一致。~~ ）。

另外，相比 LRF，LRMF 朴素下没有任何标记行为，自然要执行多少逻辑帧就会执行多少逻辑帧，自然就大概率会被兜底测算
但是一旦有不定标记行为，且不是加速模式，那么这就完全不属于任何一个已有的 LRF 环境，将直接退回到原生调度，需要结合线程行为仔细分析、理清楚帧序和时机。
这应该单独声明一下，目前暂时叫 LRIF （I 是 Indefinite），或者明确声明需要仔细分析什么的。


注意：
首先把逻辑帧的符号L记成“左”、渲染帧的符号R记成“右”是不恰当的。
~~（说点不恰当的：C++的左值右值起码还能字面理解，但是在这里这样去记是何意味呢。你说对吧。）~~
LRSF 是有渲染操作的，是 LRF 的多逻辑帧加强版。但并不能算作是 LRMF 的可控版。
> ### 原因：
> LRSF 之所以有可控个逻辑帧，是因为 LRSF 只在 LRF 的环境的基础上，推迟了单个渲染帧内渲染的时机，使其能够执行多个逻辑帧，而通过计数、if判断等方式控制时机，自然可以让逻辑帧的数量可控
> 换句话说， LRSF 仅仅在 LRF 的基础上，严格控制并允许了多个逻辑帧同时存在于一个渲染帧中，而其他操作、行为、性质都是完全不变的
> 关键的来了：所以 LRSF 也和 LRF 一样，是有等待一个帧时长的行为的。
> 但问题是， LRMF 是加速模式、无刷（没有标记渲染标记）的环境，所以其渲染操作其实是被动兜底的（在距离上一次渲染有一个帧时长时会强制渲染（而判定时机必须在逻辑帧执行完以后））
> 而被动兜底的渲染是不产生等待一个帧时长的行为的。（不然就是两个帧等待了，Scratch的内核不会停下来执行）
> 所以 LRSF 并不是 LRMF 的可控版本

说白了：
LRSF 也会强制等待帧时长。 
最严格的说法 LRSF 就是把单个逻辑帧换成了多个逻辑帧，性质不变。  
不是 LRMF 那种被动触发的不等待帧时长性质。

整理成表格类似
|模式|单个渲染帧内逻辑帧的数量|是否可控|是否等待帧时长|可能的场景|
|:-:|:-:|:-:|:-:|:-:|
|LRF|1|- <span style="opacity:0.5;">（或者说本来就恒定）</span>|是|朴素可玩可看的项目，粗略得到初步帧结论时的研究环境|
|LRMF|多个|被动|否|在现象层面精确进行帧研究时的环境<br>（说白了就是在编辑器层面进行调试）|
|LRIF|[ 需要具体分析 ]|[ 需要具体分析 ]|[ 需要具体分析 ]|极其特殊的调度情况|

这对研究其实很有帮助。
一般我先用 LRF 的环境测试和帧有关的结论、现象，粗暴的把两种帧混为一谈。
这样的好处是渲染帧的前后操作的时机的或内部行为和逻辑帧的前后操作的时机或内部行为就合并成一个帧的前后时机或内部行为了，不用纠结到底是哪个帧，而且这样子得到的结论基本可以直接运用到一般的项目中（朴素可玩可看的项目几乎都是 LRF ）
而后需要精确测试时，再考虑 LRMF 的环境进行严格测算。
再对照源码，有关帧的结论就这么出来了。
而 LRSF 多是用于一个新的计算模式，一般研究时考虑 LRMF 就行了，因为 LRMF 和 LRSF 的差别就是可控和多一个无伤大雅的等待一个帧时长的区别，不会有很大的区别。

# 补充和强调
关于调度，**一定是先有线程或旗下积木的行为，才有帧行为**，而不是反过来
这些术语是后验的，是对研究线程的总体行为的一种归纳，方便描述或者阐明总体行为，而不是先验的框架
一般来说：
LRF：稳定的一帧一逻辑帧；如果你能保证时时刻刻有标记渲染标记的行为，且不是加速模式，你才能说这是 LRF
LRMF：无标记，多逻辑帧；如果你能保证时时刻刻都没有标记渲染标记的行为，或者加速模式无视标记（行为等价），你才能说这是 LRMF
LRMIF：标记时机不定，需结合具体线程行为分析；如果你实在不能保证某坨线程符合什么LRF还是LRMF，即那种不定行为时，你才可能需要用 LRMIF 暂时声明一下该调度需要具体分析。

另外，在不能很理解调度之前，最好还是不要用这些很依赖具体示例的符号
一般这些符号也只是在结论、研究具体调度行为时出现，稍微了解一下意味着什么就行了。
调度文章也不会在讲原理讲行为时使用这些恶心的后验术语。
平时也不建议你特别把这些符号挂嘴边，即使很多现有项目确实都是LRF，即使很多精确研究确实基于LRMF环境。

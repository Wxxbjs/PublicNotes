# 积木
## 定义分类声明与引入
### 由积木特征诱导的分类（不太标准，仅用作口语描述时的明确）：
可以往下往上进行拼接的积木，可称为 块级积木 或 块（如 `[移动(10)步]`）；
若只可以往下拼接，可称为 帽子积木 或 事件积木（如 `[当绿旗被点击时]`）；
若只可以往下拼接，可称为 尾块积木 或 无尾积木（如 `[删除此克隆体]`）；
若积木槽位带有分支，可称为 C型积木 或 分支积木，（如 `[如果<>那么]{}`）
部分 C型积木 按照语境可能也称为 循环积木，仍然属于这一类（如 `[重复执行]{}` ），
部分积木根据形状可能在某些语境下称为 E型积木，但本质上都带有 分支特征
（Tips：这个严格意义上不属于积木种类，理应属于积木槽位特征，因为内核主要只有 块级特征积木(不带返回值，无论可拼接的部分是否残缺) 和 带返回值积木 两种积木种类）；
带返回值积木 或 报告器(或 报告器积木) 指 可拼接到 其他积木 的 积木槽位 上的一类积木（如 `(()+())` 和 `<<>或<>>`) ）；
圆形积木 是指 在 带返回值积木 的基础上，形状外观为 圆形 的一类积木，（如 `(()+())`）
六边形积木 或 布尔值积木 是指 在 带返回值积木 的基础上，形状外观为 六边形 的积木，（如 `<<>或<>>`）

注意，这种分类不是互斥的，可能会同时存在满足多个上述特征的积木

### 积木分类（正经）
内核主要的只有

- 块级特征积木（也称命令块，不带返回值的，无论可拼接的部分是否残缺）<br>
（帽子积木(即事件积木) 和 无尾积木 也属于这个范畴，如果某些极其特殊的扩展积木故意残缺两个方向，严格意义上也属于这个范畴）
- 带返回值积木（即报告器积木，无论 形状/类型）

两种积木种类

### 积木上的各种组件
#### 积木槽位（input/inputs）：
目前的内核主要分为 带返回值积木槽位(或 报告器槽位) 和 块级特征积木槽位 ，
字面意思：可拼接对应 积木种类 的槽位
带返回值积木槽位 可能更熟悉的两个名字 是 圆形积木槽位、布尔值积木槽位，但这其实是子类型了
块级特征积木槽位 可能更熟悉的名字 是 分支(分支积木槽位)
而三者都属于 积木槽位 旗下
这不同子种类的积木 在拼接到  积木槽位 上时可能会有限制，
如 圆形积木 无法拼接到 布尔值积木槽位(六边形) 上，
而 布尔值积木 却可以拼接到 圆形积木槽位 上，

对于一个积木槽位上所拼接的积木，存在一种叫 **阴影积木** 或 **阴影锁定** 的概念（**shadow**）
指 **被嵌在积木槽位上无法分开的积木** 和 **使得积木被嵌在积木槽位上无法分开的 行为 或 状态** 
注意，积木槽位 本身并没有任何积木，而是纯粹的 空槽位
阴影积木 可以被 再拼接的积木 “覆盖”，但**不会消失**，移除非阴影积木后可发现仍然存在
或者说 空槽位本身、阴影积木、随时可拆卸的那层积木(非阴影积木) 互相独立
在运行时，优先取“最上层”的积木执行相关逻辑，无论是解释模式还是编译模式
即对于一个槽位具体的优先级总有：非阴影积木 ->  阴影积木 -> 空槽位

Tips：
所谓的 输入框 或 积木输入框，其实是被阴影锁定的 一类特殊的积木
常见的有 字符串输入框积木 、数组输入框积木、颜色输入框积木、音符输入框积木 等，
对应的，可以输入字符串、输入数字、选择颜色、选择音高 等
这些积木其实是独立的积木对象（有点废话），本身并不一定是阴影积木，
通过一定手段可以得到可随意拖拽拼接的积木

阴影积木并不少见
如 `[移到(随机位置)]`，这个 圆形积木槽位 上的“菜单”，本体只是一个带有菜单的圆形积木，只是被阴影锁定了。
所以你才能用其他积木覆盖上去

## 积木AST结构
### 总抽象
sb3的project.json 、 Blockly 甚至 以svg渲染的dom结构、vm运行时和vm编译 中 各路 积木对象 有着惊人的相似结构
对于每个积木对象而言，所有相关表达基本上都遵循这么一个模式：
- next：指向所拼接的下一个积木，即往下拼接的积木
- parent：如果是块级特征积木，指向所拼接的上一个积木；否则指向 外层积木 ，即持有当前积木所在 积木槽位 的 上层积木
- inputs：持有的下游积木槽位，一个键值对，键为 槽位名 ，值为积木槽位对象，再细分为 阴影积木对象 和 非阴影积木

一些小性质：
- 若next不为null则 充分说明 该积木对象 属于 块级特征积木
- 若 该积木对象 属于 报告器积木，则其next必然为null

简单的说：
**同级并列的链式指向靠next，嵌套的归属靠parent（即是 槽位 也可能是 往上游方向并列 ），向子树方向产生层级嵌套靠inputs**
比如这段：
```txt
[当绿旗被点击时]
[如果<(1)=(1)>那么]{
    [移动(10)步]
    [移动(20)步]
}
[否则]{
    [移动(30)步]
}
[移动(40)步]
```
积木结构，在各种表达的 积木对象 中环境中，对每个 积木对象 总有如下关系：
`[当绿旗被点击时]` 的 next 指向`[如果<>那么]{}[否则]{}` ，parent 指向 `null`
`[如果<>那么]{}[否则]{}` 的 next 指向 `[移动(40)步]` ，parent 指向 `[当绿旗被点击时]`，inputs 中 的 `SUBSTACK`(第一分支) 指向 `[移动(10)步]` ，`SUBSTACK2`(第二分支) 指向 `[移动(30)步]` ，`CONDITION`(布尔值积木槽位) 指向 `<(1)=(1)>` ，
`<(1)=(1)>` 的 next 指向 `null` ，parent 指向 `[如果<>那么]{}[否则]{}`
`[移动(10)步]` 的 next 指向 `[移动(20)步]` ，parent 指向 `[如果<>那么]{}[否则]{}`
`[移动(20)步]` 的 next 指向 `null` ，parent 指向 `[移动(10)步]`
`[移动(30)步]` 的 next 指向 `null` ，parent 指向 `[如果<>那么]{}[否则]{}`
`[移动(40)步]` 的 next 指向 `null` ，parent 指向 `[如果<>那么]{}[否则]{}`
（这里的其他inputs和可能的阴影积木并没必要展开，暂时忽略）

注意，这里并不把 带返回值的积木 的分支视为异类，
即使在TurboWarp及其上下游分支基本都没法正常渲染这种积木，
但参考 PenguinMod 对这方面的全面处理，我觉得限定域没必要那么死其实。我倒觉得那是pm的上游们的blockly本身的集体缺陷。

blocks是对象池，以 ID映射 积木对象
对于积木对象来说，next 和 parent 和 inputs中每个槽位，并不直接指向 对象（即不是JSON），
而是存储ID（字符串）来间接指向积木对象、表示积木AST结构

对于积木对象本身新增的几个属性：
|属性|意义|
|:-:|:-:|
|opcode|积木种类，不同opcode意味着不同种的积木行为<br>一般是 `"扩展名_子积木种类名"`的形式，常见的也有 `"扩展名_menu_菜单名"`|
|fields|字段所存储的信息，键值对，键为字段名称，值为一个两元素数组<br>第一元素为 字符串/文本值<br>第二元素为指针（一般也是字符串类型），指向 变量、列表、广播 等对象的ID|
|shadow|该积木是否在parent旗下 被要求进行 阴影锁定|
|topLevel|在一段积木段中，最外层最顶上的积木为总为true，其余积木为false<br>（第二判定：顺着parent走到头，当parent为null，topLevel就为true，否则就为false）
|x/y|只有topLevel为true才具有这类属性，表示积木在工作区的坐标<br>（显然根据语义，除第一积木（toplevel），旗下整个积木段位置层级关系可以确定积木段形状）|

（这么看，在json里存topLevel有点多余了其实。`parent===null`已经充分了。）

自制积木暂时不考虑收录，主要是光是 突变属性 就可以唠半天。

input属性下的每一个 槽位对象 的数组
若元素一为：
1 -> 则下一个元素将描述阴影积木
2 -> 则下一个元素将描述非阴影积木，且槽位本身并没有阴影积木
3 -> 则是覆盖关系，下一个元素将描述非阴影积木，再下一个元素将描述阴影积木

简单理解：
在2位二进制视角下

- 低一位表示是否有阴影积木
- 高一位表示是否有非阴影积木

后续的元素意义则依次表示所激活的积木，从非阴影到阴影
（这个设计还是挺优雅的）

一个小性质：
对于2和3，读取的第一个积木对象一定是非阴影积木
对于1和3，读取的最后一个积木对象一定是阴影积木

特别的，如果一个 槽位 上没有任何积木，那么序列化时不会构造此键值对

在 槽位对象 下 描述积木 时，有三种可能：
- 数组：则是sb3序列化的**内联输入**语法，对应scr内置的一类特殊的输入框积木（如 [4,"10"] ，第一个元素为4及以上（具体意义请查表，见scratch的wiki或相关源码），接下来的一个元素是存储的数据（在4的意义下是 数字输入框积木，而对于[10,"0"]，在10的语义下是 字符串输入框积木））
- 字符串：则是积木对象的引用/指针，即当前积木对象所处在的 blocks 下的积木ID
- null：则表示没有积木，为空（少见，但是确实有这么序列化的）

注意：
对于 积木对象 的阴影锁定（并非特殊输入框积木，因为那是用 内联输入 构造的）
当 某个积木槽位 引用 该积木对象
那么必须在引用该积木对象的 槽位对象 的 数组 的元素意义上是在描述阴影积木，且积木对象本身的shadow为true，那么才被严格认为是 阴影积木 ，否则认为是 非阴影积木
如果按照上述策略解析后，发现同一个槽位上有多个非阴影积木（冲突），则默认更靠后的对象是真正的非阴影积木，另一个将直接被忽略或者被提升为孤立块（独自成积木段），取决于具体的上下文和实现

# 正文
解释模式：
相当准确：
单个线程从warp模式开始的计时器（或线程执行回归时，warp计时器重置）积攒0.5s即可触发线程让步，每个线程彼此独立

编译模式：
合理猜测：
损耗时间是单个逻辑帧累加，上界0.5s
但默认独立的每个warp模式下的自制积木（附带warp的情况没测但是由于warp讲动态传递和触发所以可以推广为warp模式而非对焦自制积木，只不过是计数而已）在单个逻辑帧内至少在 每个独立的自制积木的原型的 内部累计循环数 达到某种和100次循环相关的统计数据后才考虑让步（取执行到循环末尾的次数，看直接自制积木的原型，而不是运行时的调用对象）
因此通过 多次调用单次不足100次循环的函数来绕过的方法是不行的；
如果在执行过程中发现要调用的自制积木已经“锁了”（即现在一定被达到了0.5s，且要调用的自制积木已经达到差不多100次循环了）
那么当前线程会直接让步；

但是我不知道为什么：
先不达到0.5s，只跑60循环；
再使得超时达到0.5s条件满足；
再跑60循环；（和0.5s达到前的同一个自制积木）
每一个逻辑帧采取上面的逻辑；
会出现：（前后数字分别为第一个调用的循环数和第二个调用的循环数，是累加不是单次）
60-40 => 120-60 => 180-120 => 240-120
这种诡异的数据
而且还有
60-60 => 120-60 => 180-120 => 240-180 => 300-180
这种测不准的美感。（到底美在哪。）

简单的说：
你循环一次，当前所在的积木段的自制积木的内部就会计数+1，达到100次就开始考虑让步
因此你不能用“1+1+1+1+……+1”的手段绕过这个让步策略

会出现“一个死循环warp自制积木先达到损耗时间0.5s，接下来的其他自制积木都只能最多执行100次循环，跑满100循环就直接让步”的现象

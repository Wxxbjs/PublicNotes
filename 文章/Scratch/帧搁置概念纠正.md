# 正文
纠正一个长期的概念错误：

线程状态 STATUS_YIELD_TICK(3) 不是**逻辑帧搁置**，而是**渲染帧搁置**
（我服了，常规计算机科学都默认TICK（即嘀嗒）都是类似CPU嘀嗒这种**基本嘀嗒**，类比到scr中，本应该是逻辑帧的（早期的我就是这样认为的），但是在源码上和实际测试来看确实是渲染帧搁置。就很神秘知道吗。）

更改相关说辞（该状态具体如何被虚拟机处理，以及如何影响调度、如何恢复）：

- STATUS_YIELD_TICK 状态不管怎样都不会被warp模式压制，一定会让步线程
- STATUS_YIELD_TICK 在当前渲染帧内不会恢复，原线程不再被调用（会被虚拟机直接忽略）
- 在渲染帧的第一个逻辑帧内，虚拟机才会将 STATUS_YIELD_TICK 的线程恢复到 RUNTIME ，从而开始执行（后续逻辑帧不会恢复，以及忽略）

所以 STATUS_YIELD_TICK 是**以渲染帧**为周期进行恢复，在每个渲染帧内部，若干逻辑帧进行持久化强制让步的

以下是相关源码：

步进线程池（取自TurboWarp src\engine\sequencer.js 中对 Sequencer 类的 stepThreads 方法的定义）：
```js
/**
 * Step through all threads in `this.runtime.threads`, running them in order.
 * @return {Array.<!Thread>} List of inactive threads after stepping.
 */
//步进线程池（我们伟大的渲染帧！！！）
stepThreads () {
    // Work time is 75% of the thread stepping interval.
    const WORK_TIME = 0.75 * this.runtime.currentStepTime;
    // For compatibility with Scatch 2, update the millisecond clock
    // on the Runtime once per step (see Interpreter.as in Scratch 2
    // for original use of `currentMSecs`)
    this.runtime.updateCurrentMSecs();
    // Start counting toward WORK_TIME.
    this.timer.start();
    // Count of active threads.
    let numActiveThreads = Infinity;
    // Whether `stepThreads` has run through a full single tick.
    let ranFirstTick = false;
    const doneThreads = [];
    // Conditions for continuing to stepping threads:
    // 1. We must have threads in the list, and some must be active.
    // 2. Time elapsed must be less than WORK_TIME.
    // 3. Either turbo mode, or no redraw has been requested by a primitive.
    //我们伟大的逻辑帧！！！（若干逻辑帧）
    while (this.runtime.threads.length > 0 &&
            numActiveThreads > 0 &&
            this.timer.timeElapsed() < WORK_TIME &&
            (this.runtime.turboMode || !this.runtime.redrawRequested)) {
        if (this.runtime.profiler !== null) {
            if (stepThreadsInnerProfilerId === -1) {
                stepThreadsInnerProfilerId = this.runtime.profiler.idByName(stepThreadsInnerProfilerFrame);
            }
            this.runtime.profiler.start(stepThreadsInnerProfilerId);
        }

        //我们伟大的逻辑帧！！！（单个逻辑帧）
        numActiveThreads = 0;
        let stoppedThread = false;
        // Attempt to run each thread one time.
        const threads = this.runtime.threads;
        for (let i = 0; i < threads.length; i++) {
            const activeThread = this.activeThread = threads[i];
            // Check if the thread is done so it is not executed.
            if (activeThread.stack.length === 0 ||
                activeThread.status === Thread.STATUS_DONE) {
                // Finished with this thread.
                stoppedThread = true;
                continue;
            }
            //线程被STATUS_YIELD_TICK，且这是第一个逻辑帧（当!ranFirstTick为true）
            //这证明了帧搁置的时序，所以帧让步是以渲染帧为周期，在第一个逻辑帧内恢复
            //而不是单个逻辑帧
            if (activeThread.status === Thread.STATUS_YIELD_TICK &&
                !ranFirstTick) {
                // Clear single-tick yield from the last call of `stepThreads`.
                activeThread.status = Thread.STATUS_RUNNING;
            }
            //我们伟大的执行线程！！
            //证实了运行时状态和单纯搁置都会导致执行
            if (activeThread.status === Thread.STATUS_RUNNING ||
                activeThread.status === Thread.STATUS_YIELD) {
                // Normal-mode thread: step.
                if (this.runtime.profiler !== null) {
                    if (stepThreadProfilerId === -1) {
                        stepThreadProfilerId = this.runtime.profiler.idByName(stepThreadProfilerFrame);
                    }

                    // Increment the number of times stepThread is called.
                    this.runtime.profiler.increment(stepThreadProfilerId);
                }
                this.stepThread(activeThread);
                activeThread.warpTimer = null;
            }
            if (activeThread.status === Thread.STATUS_RUNNING) {
                numActiveThreads++;
            }
            // Check if the thread completed while it just stepped to make
            // sure we remove it before the next iteration of all threads.
            if (activeThread.stack.length === 0 ||
                activeThread.status === Thread.STATUS_DONE) {
                // Finished with this thread.
                stoppedThread = true;
            }
        }
        // We successfully ticked once. Prevents running STATUS_YIELD_TICK
        // threads on the next tick.
        ranFirstTick = true;

        if (this.runtime.profiler !== null) {
            this.runtime.profiler.stop();
        }

        //我们伟大的过滤失活线程！！！
        // Filter inactive threads from `this.runtime.threads`.
        if (stoppedThread) {
            let nextActiveThread = 0;
            for (let i = 0; i < this.runtime.threads.length; i++) {
                const thread = this.runtime.threads[i];
                if (thread.stack.length !== 0 &&
                    thread.status !== Thread.STATUS_DONE) {
                    this.runtime.threads[nextActiveThread] = thread;
                    nextActiveThread++;
                } else {
                    this.runtime.threadMap.delete(thread.getId());
                    doneThreads.push(thread);
                }
            }
            this.runtime.threads.length = nextActiveThread;
        }
    }

    this.activeThread = null;

    return doneThreads;
}
```

当然，我更推荐直接写一个扩展怼着线程进行yieldTick来让步，看看线程什么时候会回归调用yieldTick的积木
（现象就是：只在每个渲染帧的第一个逻辑帧进入积木函数的逻辑（即调用线程）；同时不会被warp模式下的自制积木卡死）

另外碎碎念一下：
STATUS_YIELD_TICK 也好 STATUS_YIELD 也罢
解释模式调用 util.yield() 也好 ，util.yieldTick() 也罢
编译模式利用 function* 与 yield 指令也好
其实都有一个性质：
**被什么积木搁置，当线程恢复执行时，就从什么积木开始调用**（或者编译模式中一个模糊的上下文的关系，但是不管怎样，道理都是类似）
所以在一个积木 yield 了（各种方式），下一次恢复时绝对是先回归到当前这个积木的
所以让步的本质是在**一个积木内发生的**，该积木 **独立开始组织策略** 和 **被多次调用** 来权衡是否“放行线程”而不是继续控制在当前积木函数内部

关键是你得知道：线程让步是**集中在一个积木上**，该积木**独立控制**是否“放行线程”，或者继续让步
所以为了能体现这点，scr会让线程每次恢复时反复调用这个积木的整个逻辑，直到这个积木不让步了
对每个有让步逻辑的积木都是如此
所以，控制积木（比如等待秒数和等待条件）内部都是差不多的理念。
所以我想告诉你的就是：让步不是具体到在积木对应的函数内具体的执行位置，而是线程恢复时，直接重跑整个函数
所以写扩展的时候要注意：整个函数就是一个抽象的“循环”
而不是`while(true){if(pd)util.yield();}`的写法，这是不对的。

而考虑到会重跑函数，所以Scratch提供了一些接口来持久记录状态
你应该在自己的扩展里依赖于 util.stackFrame 来保存对于单个积木内部的持久化状态（原理是在栈顶（当前积木）的一个独立上下文对象，你不需要用 util.stackFrame() 来显式进行函数调用，因为在实现util的class实现上已经用get修饰了）

所以，对于一个标准的等待积木而言，应该这样写逻辑：
```js
sleep(args, util){
    const NUM=Scratch.Cast.toNumber(args.NUM);
    const frame = util.stackFrame;
    if (frame.startTime === undefined) {
        frame.startTime = Date.now();
    }
    if (Date.now() - frame.startTime < NUM) {
        util.yield();
        return;
    }
}
```
当然这只是示例。实际上就是告诉你怎么用利用Scratch的让步机制。

偶对了，再说一下：
`util.yield()`等这类接口不是什么高级js语法，所以**不可能影响函数执行、调用栈**，这些指令背后的原理**只是设置线程状态**，而**不是搁置函数**
只有你这个函数跑完了，Scratch才知道线程现在是什么样的，怎么去转移状态
所以:
- 如果你不确定是不是一定不会在`util.yield();`后执行其他代码，那么就请一定要考虑直接return结束函数
- 如果你的逻辑清晰，可以保证 yield 后无代码执行时，可以考虑省略。（但一般不推荐）
